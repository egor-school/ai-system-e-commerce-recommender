# Постанока задачи
### Бизнес-цель
Повысить конверсию и средний чек e-commerce платформы за счёт автоматической персонализированной выдачи релевантных товаров каждому пользователю в реальном времени, обеспечив при этом быстрый отклик (ANN-поиск + бустинг-ранжирование) и эффективное использование всего каталога, включая «длинный хвост».

### Конечный потребитель
Клиент платформы (B2C-покупатель), а также оператор/маркетолог через панель управления и внешние учётные системы (ERP/PIM/CRM) через API-интеграцию.

### Метрики эффективности:

 **Метрики бизнес-процесса:** рост конверсии из показа рекомендаций в покупку ( с 1.2% до 2.0%); увеличение доли GMV из рекомендаций ( с 12% до 25% от общей выручки); рост среднего чека заказов с рекомендованными товарами ( +10%); повышение retention D30 ( с 22% до 28%); рост CTR рекомендательного блока ( с 4% до 8%).

**Технические метрики (SLA):** время ответа сервиса (p95 < 200 мс); -пропускная способность (RPS ≥ 500); доступность (99.9%); доля ошибок 5xx (< 0.1%); свежесть эмбеддингов каталога (< 24 ч).

**Метрики качества модели:** Recall@100 ≥ 0.85; NDCG@10 ≥ 0.45; ROC-AUC (pCTR) ≥ 0.80; ROC-AUC (pCVR) ≥ 0.78; GAUC ≥ 0.65; калибровка ECE ≤ 0.05.

### Границы системы:

**Входит в систему:** валидация данных, генерация эмбеддингов каталога, инференс (ANN-поиск + бустинг-ранжирование), логирование, API, локальное хранение метаданных.

**Не входит в систему:** оформление и оплата заказа, управление складскими остатками и логистика, ценообразование и промо-движок, бухгалтерский и налоговый учёт, клиентская поддержка и возвраты, юридическое согласование документов.

### Описание информационных потоков
1.  **Покупатель <-> System:** Протокол HTTPS (REST API). Частота: при каждом открытии карточки товара или главной страницы (примерно 50-200 запросов в секунду). Формат: JSON (ID сессии, ID текущего товара -> массив ID рекомендовых товаров с весами).
2.  **System -> CorpDB:** Протокол gRPC / SQL connection. Частота: On-demand (кэширование в Redis внутри системы для снижения нагрузки). Формат: структурированные профили пользователей и история покупок.
3.  **System -> AlertSystem:** Протокол HTTPS (Webhooks API). Частота: асинхронно, только при возникновении критических ошибок (5xx) или падении бизнес-метрик. Формат: JSON-текст алерта.
4.  **System -> Monitoring:** Протокол HTTP (Pull-модель Prometheus). Частота: каждые 15 секунд. Формат: OpenMetrics (plain text).

    score: float = Field(ge=0.0, le=1.0, description="Скор уверенности/релевантности модели")

    request_id: str = Field(description="Уникальный идентификатор запроса (UUIDv4) для сквозного аудита")

### ADR-01: Выбор режима инференса
* **Статус:** Принято (Accepted)
* **Контекст:** Каталог содержит сотни тысяч товаров. Прямое ранжирование всех позиций через CatBoost при каждом HTTP-запросе нарушает SLA (требуется p95 < 150 мс).
* **Альтернативы:** 1. Полный онлайн-инференс; 2. Офлайн-расчет (Batch); 3. Двухстадийный инференс.
* **Решение:** **Двухстадийный инференс (Candidate Generation + Online Ranking)**. На 1 шаге векторный поиск (ANN) отбирает ~100 кандидатов. На 2 шаге CatBoost их сортирует.
* **Обоснование:** Обеспечивает баланс точности и скорости. Система укладывается в SLA (<150 мс) и учитывает контекст сессии «на лету».
* **Последствия:** Усложнение кода: необходимо поддерживать и синхронизировать две разные ML-модели.

### ADR-02: Версионирование и обогащение признаков (Feature Store)
* **Статус:** Принято (Accepted)
* **Контекст:** Модели нужны исторические фичи (средний чек, популярность товара). Расчет через SQL-запросы при инференсе завалит SLA. Есть риск Train-Serving Skew.
* **Альтернативы:** 1. On-the-fly SQL-запросы; 2. In-Memory кэш приложения; 3. Выделенный Feature Store (Redis).
* **Решение:** **Слой признаков на базе Redis (Online Feature Store)**. Агрегированные в офлайне фичи загружаются в Redis. Приложение считывает их по ключам за <2 мс.
* **Обоснование:** Redis гарантирует минимальные задержки. Использование единых фичей для обучения и инференса исключает Train-Serving Skew.
* **Последствия:** Дополнительные затраты на RAM для Redis и необходимость настройки процессов инвалидации кэша.

### ADR-03: Версионирование артефактов моделей
* **Статус:** Принято (Accepted)
* **Контекст:** Эмбеддинги товаров (~2 Гб) и веса CatBoost (~150 Мб) нельзя хранить в Git — это раздувает репозиторий и нарушает правила разработки.
* **Альтернативы:** 1. Git LFS; 2. Реестр моделей MLflow; 3. Связка DVC + S3 (MinIO).
* **Решение:** **Использование DVC и S3-хранилища (MinIO)**. В Git коммитятся только файлы-указатели `.dvc`. Сами веса скачиваются через `dvc pull` при сборке Docker-образа.
* **Обоснование:** Чистый Git-репозиторий и 100% воспроизводимость. Конкретный коммит строго привязан к своей версии весов в S3.
* **Последствия:** Требуется администрирование MinIO и управление доступами в CI/CD пайплайнах.

### Информационная безопасность и защита данных
* **Аутентификация:** Проверка статического токена в заголовке `X-API-Key` через Middleware в FastAPI.
* **Защита от DoS:** Ограничение размера Payload на уровне Nginx до **2 Мб**; Rate Limiting в Redis — не более 20 запросов/сек для одного `user_id`.
* **152-ФЗ и приватность:** Полное исключение ПДн (ФИО, email) из контура ИИ. Модели и базы данных оперируют только обезличенными хэшами `user_id` и `item_id`.

### Наблюдаемость (Observability) и аудит
* **Формат логов:** Структурированный JSON в `stdout` для Grafana Loki:
  ```json
  {"timestamp": "2026-09-28T19:30:00Z", "level": "INFO", "request_id": "uuid", "user_id": "123", "latency_ms": 45.2, "status": 200, "model_version": "catboost_v1.0"}
  ```
* **Метрики Prometheus:**
  * `http_requests_total` (счетчик запросов по кодам ответа);
  * `recommender_ann_search_duration_seconds` (время отбора кандидатов);
  * `recommender_ranking_duration_seconds` (время ранжирования CatBoost).
* **Борьба с дрейфом (Data Drift):** Входящие ID товаров и скоры рекомендаций пишутся в ClickHouse. Раз в неделю скрипт на базе **Evidently** считает метрику PSI (Population Stability Index). При PSI > 0.25 инженерам отправляется алерт в Telegram о необходимости переобучения моделей.
